# MUARÉ — Staging и Production Runbook

Дата: 12.08.2026

## 1. До выпуска

- рабочая ветка чистая, commit опубликован в `main`;
- `npm run check` и `npm audit --omit=dev` успешны;
- настроены `DATABASE_URL`, `AUTH_SECRET`, `AUTH_TRUST_HOST`, `SEED_STAFF_PASSWORD` только в защищённых переменных окружения;
- `AUTH_TRUST_HOST=true` используется только за доверенным reverse proxy или на выбранном хостинге;
- staging и production используют разные PostgreSQL-базы;
- подтверждены домен, `NEXT_PUBLIC_SITE_URL`, часовой пояс `Europe/Moscow` и владелец резервных копий.

## 2. Резервная копия

Перед миграцией production создать snapshot у PostgreSQL-провайдера или логический
backup штатным инструментом провайдера. Проверить, что backup имеет дату, размер,
шифрование и срок хранения. Не сохранять дамп в Git-репозитории.

До первого production-release выполнить тестовое восстановление backup в отдельную
базу и проверить количество организаций, пользователей, мастеров и записей.

## 3. Миграции

Для production применяются только уже созданные миграции:

```bash
npx prisma migrate deploy
npm run prisma:generate
```

Запрещены `prisma migrate reset`, редактирование применённых миграций и удаление
рабочих данных. После применения сверить статус миграций и основные таблицы.

## 4. Staging smoke

1. Открыть все публичные страницы.
2. Отправить тестовую `PENDING` заявку.
3. Убедиться, что слот исчез из доступности.
4. Войти администратором, подтвердить, перенести и отменить тестовую запись.
5. Войти назначенным мастером и проверить только собственное расписание.
6. Проверить мобильную ширину 360 px и клавиатурную навигацию.
7. Убедиться, что защищённые URL без сессии перенаправляют на вход, а API возвращают `401`.

## 5. Выпуск и наблюдение

После production deploy повторить короткий smoke без изменения реальных клиентских
данных. Проверить HTTP 5xx, ошибки базы, время ответов availability и создание заявок.
Секреты, телефоны клиентов и пароли не должны попадать в журналы.

## 6. Откат

При ошибке приложения вернуть предыдущий проверенный deployment. Если миграция
необратимо изменила данные, остановить запись новых данных и восстановить подтверждённый
backup в отдельную базу, затем переключить приложение по процедуре провайдера.
Не выполнять ручной destructive SQL без отдельного согласования и проверенного плана.

## 7. Решение о запуске

Production release разрешён только после успешных P0 из `TEST_PLAN.md`, staging smoke,
проверенного backup/restore и назначенного ответственного за откат.
