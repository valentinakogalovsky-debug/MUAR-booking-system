# AGENTS.md

## 1. Обязательный контекст

Перед началом любой задачи обязательно изучить:

1. `README.md` — обзор репозитория и фактическое состояние.
2. `spec.md` — утверждённые требования и границы продукта.
3. `PLAN.md` — последовательность и статус реализации.
4. Связанные документы в `docs/`.
5. Подходящий skill из `.agents/skills/`.

`spec.md` отвечает на вопрос «что строим», а `PLAN.md` — «в каком порядке и что уже
сделано».

### Стоп-правило при конфликте

При любом конфликте `PLAN.md` и `spec.md` работа немедленно останавливается.

ИИ запрещено:

- самостоятельно выбирать один из вариантов;
- молча исправлять один документ по другому;
- менять код, схему БД или тесты до решения конфликта;
- выдавать предположение за утверждённое требование.

Нужно сообщить точные противоречащие положения, их расположение и влияние на
реализацию, затем запросить решение пользователя. После решения сначала
синхронизировать `spec.md` и `PLAN.md`, затем продолжить задачу.

## 2. Границы проекта

- Не менять архитектуру приложения без отдельного задания.
- Не менять утверждённый стек технологий.
- Не удалять и не отключать существующий функционал.
- Не менять структуру базы данных без новой миграции.
- Не менять названия маршрутов страниц и API без обоснованной необходимости.
- Не добавлять сторонние библиотеки без необходимости и объяснения причины.
- Не выполнять несвязанный рефакторинг в рамках локальной задачи.
- Не менять утверждённые бизнес-правила без явного указания пользователя.
- Не восстанавливать роль `CUSTOMER`, клиентскую авторизацию, кабинет клиента или
  маршрут `/my-bookings`.
- Не подтверждать публичную заявку автоматически: начальный статус — `PENDING`.
- Не исключать `PENDING` из статусов, блокирующих слот.
- Не заменять комбинированный визит одного мастера длительностью 180 минут работой
  двух мастеров или двумя независимыми бронями.
- Не менять контент, дизайн, маршруты или публичную структуру без задания.
- Не перезаписывать и не удалять несвязанные пользовательские изменения.
- Не выполнять разрушительные Git-команды.

## 3. Работа с базой данных

- Любое изменение `prisma/schema.prisma` сопровождать новой миграцией.
- Не редактировать уже применённые миграции задним числом.
- Не выполнять `prisma migrate reset` или другие команды сброса без явного запроса.
- Не удалять пользовательские или рабочие данные.
- Не обходить ограничения PostgreSQL и серверные проверки доступности.
- Не выводить `DATABASE_URL`, пароли, токены и другие секреты.
- После изменения схемы выполнять `npm run prisma:validate` и
  `npm run prisma:generate`.
- Критические правила бронирования проверять на сервере, а не только в интерфейсе.

## 4. Работа с UI

- Не переписывать экран полностью ради небольшой правки.
- Использовать существующие компоненты, токены и дизайн-систему MUARÉ.
- Не менять дизайн, тексты или структуру страниц без задания.
- Сохранять адаптивность, доступность и существующие пользовательские сценарии.
- Не дублировать серверную бизнес-логику в клиентских компонентах.

## 5. Безопасность и доступ

- Проверять авторизацию и разрешения для каждой защищённой серверной операции.
- Не доверять `userId`, `organizationId`, роли, цене и длительности с клиента.
- Не раскрывать данные других клиентов или мастеров через прямые ссылки и API.
- Валидировать входные данные на сервере.
- Не передавать хеши паролей и служебные данные на клиент.
- Не добавлять клиентские права через скрытие кнопок без серверной проверки.

## 6. Порядок работы

Перед изменениями:

1. Изучить связанные документы и файлы.
2. Проверить текущее состояние Git и не затрагивать несвязанные изменения.
3. Определить минимальный набор файлов для задачи.
4. Отдельно предупредить, если требуется миграция, новая зависимость или изменение
   архитектуры.

После изменений:

1. Проверить diff и отсутствие случайных изменений.
2. Выполнить обязательные проверки.
3. Исправить ошибки, относящиеся к задаче.
4. Не объявлять задачу завершённой при наличии критических ошибок.
5. Не выполнять commit или push при проваленных обязательных проверках.
6. Не выполнять push без прямого запроса пользователя.
7. Не запускать `npm audit fix --force`.

## 7. Обязательные проверки

Перед завершением задачи выполнить:

```bash
npm run lint
npm run typecheck
npm run build
```

Для изменений Prisma дополнительно выполнить:

```bash
npm run prisma:validate
npm run prisma:generate
```

Если команда не была выполнена или завершилась ошибкой, явно сообщить об этом.

## 8. Итоговый отчёт

После завершения кратко сообщить:

- что было сделано;
- список изменённых файлов;
- результаты проверок;
- что пользователь может проверить самостоятельно;
- известные ограничения и возможные риски;
- следующий шаг только в пределах утверждённого `PLAN.md`.

## 9. Проектные skills

Для профильных задач использовать инструкции из `.agents/skills/`:

- `explain-before-code` — объяснить изменения до реализации;
- `create-feature` — реализовать ограниченную функцию по плану;
- `ui-component` — изменить интерфейс без смены дизайна;
- `api-endpoint` — создать серверный контракт;
- `prisma-migration` — безопасно изменить Prisma;
- `booking-business-rules` — проверить правила заявки и занятости;
- `admin-panel` — функции администратора;
- `code-review` — провести ревью;
- `update-plan` — актуализировать документацию после завершения этапа.
- `run-project-checks` — выполнить обязательные проверки проекта;
- `booking-availability` — изменить расчёт расписания и свободных интервалов;
- `authentication-permissions` — реализовать вход и серверные права;
- `test-booking-flow` — проверить заявку от интерфейса до PostgreSQL;
- `release-and-push` — подготовить проверенный commit и push по запросу.
